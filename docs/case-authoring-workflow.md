# Case 编写与导入（2026-09-10）

## 当前流程

飞书固定模板（业务目标、输入、前置条件、预期、证据、禁止行为） → Codex 生成 JSON 数组或 JSONL → `pnpm cases:validate 文件路径` → 平台选择文件自动预检 → 查看新增／修改／移除／未变化 → 确认替换 → 小批执行。

- 本地校验检查契约、断言类型／必要参数、JS 语法、重复 Case ID。不执行 JS、不调用 Agent 或 Judge。
- 平台预检另检查 Rubric 引用和测试集 Revision，并计算替换影响。确认后仍重新校验；并发冲突必须重新预检并确认。
- **导入是完整替换，不是追加。空数组会移除当前全部 Case。** 历史 Run 快照不受影响。
- 本地工具上限 32 MiB，适合生成文件的快速检查；超过限制请拆分本地检查，但正式全量替换必须提交完整集合，不能把分片依次导入同一测试集。
- 只保证配置在已实现的静态检查范围内可接受，不保证服务授权、数据准备、模型调用、业务通过或自定义代码运行成功。Provider 依赖和运行能力仍由已有运行预检负责。

## 编写约束

- `metadata.case_id` 唯一；中文描述写清目标，不用描述文本充当 ID。
- `assert[].type` 使用支持的准确名字；`metric` 是业务指标名，不是规则类型，不应把它限制成固定白名单。
- `rubricPrompt` 使用 `prompt://已有键`；存在性以服务端预检为准。
- 字段存在不等于非空：null／false／0 可是合法存在值；需要类型／精确值时组合规则。
- 精确数组比较检查顺序和重复项。实际执行规则的 sets 为无序集合且拒绝重复，不能混用两种口径。
- 观察项可以 weight=0，但整例不能全为观察项。关键业务检查必须参与最终判定，并按实际 threshold 验证阻断效果；本轮不会自动改权重或阈值。
- 计划调用不能代替实际执行证据；禁止写入等检查不能只看回复。
- JS 只做语法检查，不能静态保证语义、完整返回值或任意业务规则正确。
- 历史读取仍使用旧兼容契约；新建／编辑／导入使用严格编写契约，历史不合规 Case 修改时可能需要修正。
- 不根据实际输出倒改预期；修改须有业务规则或契约依据。

## 平台稳定性验收（下一阶段）

先做三组小集合：①正常流程 ②断言／导入错误与并发冲突 ③执行／评测失败、历史记录、人工复核。离线假响应只能证明平台处理链路，不能冒充真实 Agent 验收。真实写入 Case 必须另确认测试账号与副作用范围。CLI/MCP 与飞书自动接入留待这一步稳定后。
